Backend:
- packages should be in plural and sub classes are singular


Database:
- JPA entities should be singular
- attribute names should be in camelCase and should be kept minimal
- Primary keys should be named "id" not "tableId"
- Primary keys should be only of type UUID to keep types consistent
- Have bidirectional mapping to foreign tables
- Specify @Column annotation for all attributes
- @Entity, @NoArgsConstructor(access = AccessLevel.PROTECTED), @Getter, and @Setter should be base annotations for entities. Don't use @Data
- To test for instances equality, don't use Object.equals() and instead compare the business keys: Object1.getId().equals(Object2.getId())
- Add helper methods on the weak entity if using bidirectional mapping


Commits
- Use Angular Commit Convention ("type(scope): message")
- Message should be descriptive, and succinct
- Commits should be done per logical unit change not per file, and commits should not be micro or huge. 
- Ideally, tasks should be done in one go, but if a task requires adding a change that is not just specific to that task, then commit that change first, then commit the task. This can be prevented by just working on a general problem at once before tackling another one, especially if the next task requires depends on another feature. 
- 
- Types:
	- feat: a new feature for the user or app. Even new classes/components that introduces a feature
	- docs: anything documentation related. READMEs and comments for example
	- refactor: code change that neither is a bug fix, business logic change, or a new feature. But is a restructure of existing code/logic to improve design or structure.
	- test: anything test related
	- build: changes that affect the build system or dependencies. E.g: upgrading tech versions, or installing an external package/library
	- chore: other minor changes or "chores" that don't belong to other types. E.g: cleaning up code (removing spaces or new lines), editing, updating .gitignore, moving files.
- Scope.
  - For the most part, it should be categorized by package and state the file/s being modified in the message
  - If global relative to a layer (frontend/backend), scope should be layer/file (E.g: backend/pom.xml)
  - If global relative to the whole project, just state the file (E.g: README)
  - If multiple scopes are somewhat equally affected, they can be grouped. 
    - If the sub scopes are within the same layer, list them inside brackets: (backend/[controllers,service])
    - If the sub scopes are not within the layer, list them separetly with spaces (though this should be avoided as much as possible, if a change spans different layers, then it you must scope down and commit them separately): Pfrontend/profile, backend/controllers)
- Types...
- Examples:
  - feat(backend/repository): add CandidateRepository
  - fix(backend/models): add @Enumerated(EnumType.STRING) to Manager.role to show enum role as string
  - chore(backend/pom.xml): add spring-security
  - docs(README): add features section
  - docs(conventions): add more commit rules
